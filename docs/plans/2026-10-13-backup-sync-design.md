## 1. 产品定义

**一句话**：把 `@xiaoyuyu6420/dsh-backup` 的黑盒命令，变成「上下文洞察」那样的可视化面板——看得见有什么、勾得动备什么、导得进增量。

**入口形态**（已核实锚点）：`dsh-context`（「上下文洞察」）的 README 原文——

> Click **Context Insights / 上下文洞察** in the sidebar's panel list — the same row level as **Plugins** and **Automation tasks** — and the page opens as a full center-column panel.

因此本插件同样是：**侧边栏面板列表加一行「备份同步」，点开占据中央栏整页**。

**与 dsh-backup 的关系**：并存，不卸载。本插件生成的归档与 dsh-backup 格式同构（`tar.gz` + `.sha256` + `.meta.json`），所以两边都能恢复，不会产生「只能用本插件打开」的死包。

## 2. 架构

三层：客户端半边只负责看和点，宿主半边干活。

```
┌─ 客户端半边 lib/client.js ─────────────────────┐
│  「备份同步」面板（中央栏整页）                  │
│  模块总览 · 勾选 · 差异预览 · 冲突裁决 · 历史版本 │
└───────────────┬────────────────────────────────┘
                │ HTTP（loopback-only，仿 dsh-backup 的 /dsh-backup/settings）
┌───────────────┴─ 宿主半边 lib/index.js ────────┐
│  ① 扫描器 scan     模块 → (路径, 哈希, 大小)     │
│  ② 归档器 archive  tar.gz + sha256 边车          │
│  ③ 基线库 baseline ~/.dsh/backup-sync/state.json│
│  ④ 差分器 diff     三方比较 → 动作计划           │
│  ⑤ 执行器 apply    按计划写盘（先备份后写）      │
│  ⑥ 同步器 sync     二期：调 git                  │
└─────────────────────────────────────────────────┘
```

### 2.1 关键设计决策

| 决策 | 理由 |
|---|---|
| **扫描器与差分器分家** | 扫描要读 ~4.4 MB / 170+ 文件；差分要读整个基线库。分开才能让面板打开时只跑扫描，秒开。 |
| **复用系统 `tar`（bsdtar）而非自写压缩** | Windows 自带；与 dsh-backup 同构；纯 JS 写 tar.gz 无收益。 |
| **哈希用 `node:crypto`** | 零依赖。 |
| **同步走 `git` 子进程** | 与 dsh-backup 同款做法（credential helper + `x-access-token`），不重造。 |
| **测试用 `node:test` + `node:assert`** | Node 内置，零依赖，与插件「无第三方运行时依赖」的哲学一致。 |
| **客户端半边手写 bundle，不引入打包器** | 见 §2.3。 |

### 2.2 三条写盘不变量（硬规矩）

1. **任何写盘前先备份**到 `~/.dsh/backup-sync/pre-restore-<时间戳>/`
2. **凭据文件永不进包、永不进基线**（`.credentials.yaml` 内是明文 API key + DSH 会话密钥）
3. **归档格式与 dsh-backup 同构**，保证交叉可恢复

### 2.3 客户端半边的技术约束（风险项）

DSH 客户端插件的 `lib/client.js` 是**预构建 bundle**，形如：

```js
window.__ModuleLoader__.load({ id: `dsh-context`, factory: e => { /* … */ } })
```

工厂函数的参数 `e` 是一个 require：`e("react")`、`e("react/jsx-runtime")`、`e("@deepseek-ai/dsh-client-ui-primitives")`。

**本项目不引入 esbuild / 打包器**（本机无 DSH 源码检出，打包链路要另建）。做法是**手写 bundle 外壳**，工厂体内用 `React.createElement` 而非 JSX。代价是写法啰嗦，收益是零工具链、改完即生效。

> M2 的**第一个任务**就是逆向出 `__ModuleLoader__` 的精确契约（工厂返回什么、`inject`/`apply`/`name` 如何导出、slot 注册 API），再动 UI。这是全项目最大的未知，必须先行验证。

## 3. 数据模型

### 3.1 模块 → 文件清单映射（核心：模块按**文件模式**划，不按目录划）

| 模块 | 根 | 匹配 | 计数口径 |
|---|---|---|---|
| 技能 `skills` | `~/.agents/skills` | `**` | 技能目录数（当前 10） |
| 插件 `plugins` | `~/.dsh/profiles/<p>` | `package.json`（仅取 `dsh.profile.bundles` + `dependencies`）、`pnpm-lock.yaml`、`.npmrc`、`pnpm-workspace.yaml` | bundles 数 + deps 数（当前 12 bundle） |
| 配置 `config` | `~/.dsh/profiles/<p>` 与 `~/.dsh` | `cordis.patch.yml`；`settings.yaml`、`AGENTS.md` | 文件数 |
| 记忆 `memory` | `~/.dsh/memories` | `**`，**排除待办模式** | 文件数 / 条目数 |
| 待办 `todo` | `~/.dsh/memories` | 仅待办模式（见下） | **条目数**（四轨合计） |
| 对话 `sessions` | `~/.dsh/sessions` | `**` | 会话数 |

**待办模式**（`memories/` 树内）：

```
TODOS-life.md                      → life 轨
TODOS-work.md                      → work 轨
projects/<hash>/TODOS.md           → project 轨
daily/YYYY-MM-DD.todo.md           → daily 轨
```

**记忆模式** = `memories/**` 减去上面四条。注意 `projects/<hash>/` 下 `MEMORY.md`、`KEY.md` 归记忆，`TODOS.md` 归待办——**邻居不同模块**。

> 这一节是整个设计里最容易做错的地方：记忆与待办在同一棵树里交错，若按目录切分必然切错。

### 3.2 基线库

位置：`~/.dsh/backup-sync/state.json`

```json
{
  "version": 1,
  "machine": "<hostname>",
  "lastSyncAt": 1789000000000,
  "archives": {
    "dsh-20261013-1830.tar.gz": { "importedAt": 1789000000000, "count": 136 }
  },
  "files": {
    "skills:cdp-browser-automation/SKILL.md": {
      "sha256": "a1b2…", "size": 4213, "mtime": 1789000000000
    }
  }
}
```

文件键 = `<模块id>:<相对根路径>`。

**基线库自身必须进备份包**——否则换机后基线为空，第一次导入会把所有差异都判成「冲突」。

### 3.3 条目标识能力（决定合并粒度，已核实）

| 数据类型 | 有无稳定主键 | 合并方式 |
|---|---|---|
| `KEY.md` 条目 | ✅ `[mem-xxxxxxxx]` | 按 id 做主键合并 |
| 待办条目 | ✅ 8 位十六进制 id | 按 id 做主键合并 |
| `MEMORY.md` / `USER.md` 条目 | ❌ 只有 `[YYYY-MM-DD]` 前缀 | **按内容整行去重** |
| `daily/*.md` | ❌ | 按文件合并 + 行级去重 |
| `SUGGESTIONS.jsonl` | ❌ | 按行内容 hash 去重 |
| 技能 / 配置 / 对话 | ✅ 路径即主键 | 文件级 |

**已告知用户并获接受的取舍**：同一件事若两边都记了、但措辞不同，合并后会留两条。目标是「不丢」，不是「去重」。

## 4. 增量导入

### 4.1 为什么必须引入基线

设包里技能 A 是 10/1 版，本地是 10/10 版。只看这两份**无法区分**：

| | 真相 | 正确动作 |
|---|---|---|
| ① | 本地 10/10 改过，包是旧的 | 保留本地 |
| ② | 本地没动过，是在**另一台机器**上 10/1 之后改的 | 用包里的 |

表象完全相同（包旧、本地新），正确动作相反。唯一解法是**基线**——记住上次同步完成时每个文件的样子，从而做三方比较（`base` / `ours` / `theirs`），即 git merge 的算法。

### 4.2 三方比较矩阵（差分器核心）

| base | ours | theirs | 判定 | 动作 |
|---|---|---|---|---|
| — | — | ✓ | 包新增 | **导入** |
| — | ✓ | — | 本地新增 | 保留 |
| — | ✓ | ✓ | 双方各建 | 相同→跳过；不同→**冲突** |
| ✓ | =base | =base | 都没动 | 跳过 |
| ✓ | ≠base | =base | 只有本地改 | 保留本地 |
| ✓ | =base | ≠base | 只有包里改 | **导入** |
| ✓ | ≠base | ≠base | 双方都改 | **冲突** |
| ✓ | 删除 | ≠base | 本地删、包改 | **冲突** |
| ✓ | ≠base | 删除 | 包删、本地改 | **冲突** |
| ✓ | =base | 删除 | 包删、本地没动 | 删除本地 |

**十种情况，只有四种是真冲突。** 不冲突的自动走默认策略；界面只报一句「自动导入 37 项、保留本地 5 项、冲突 2 项待裁决」。

### 4.3 分模块默认策略（用户已选定：分模块默认 + 冲突弹差异预览）

| 模块 | 粒度 | 默认动作 | 冲突时 |
|---|---|---|---|
| 技能 | 整个技能目录 | 补齐缺失 | 弹预览：整目录「用包里的 / 保留本地」 |
| 配置 | 整个文件 | 补齐缺失 | 弹预览：逐行 diff，**默认保留本地** |
| 插件 | JSON 字段级 | `bundles` 取并集、`dependencies` 取并集 | 字段级弹预览 |
| 记忆 | 条目级（内容行去重） | 两边都留（追加） | 极少 |
| 待办 | 条目级（按 8 位 id） | 两边都留 | 同 id 不同内容才冲突 |
| 对话 | 整个会话文件 | 补齐缺失 | 弹预览 |

## 6. 错误处理

| 场景 | 处理 |
|---|---|
| 扫描时文件读不到（权限/占用） | 记入 `warnings[]`，不中断整次扫描 |
| 归档写盘失败 | 写临时文件 + 原子改名（`.tmp-<uuid>`），失败删临时文件并报错 |
| 导入中途失败 | 已写入的部分不回滚，但 `pre-restore-<时间戳>/` 保留原始副本，可手工回退 |
| 基线库损坏（JSON 解析失败） | 视为「无基线」，界面显式警告「首次同步将按无基线处理」，不静默 |
| 归档校验和不匹配 | 拒绝导入，提示重新获取 |
| 归档含凭据文件 | 拒绝导入（硬护栏，与 dsh-backup 一致） |

## 7. 测试策略

- 运行时：`node --test`（Node 内置，零依赖）
- 单测对象是**纯函数**：`modules.js` 的模式匹配、`diff.js` 的三方矩阵、`baseline.js` 的读写
- 用**临时 fixture 目录树**模拟 `~/.dsh` 与 `~/.agents`，测试注入根路径，不碰真实用户数据
- `scan.js` 的测试断言「同一个 fixture 树上，记忆与待办被正确分开」
- 三方矩阵**十种情况逐个断言**——这是全项目最容易出错的逻辑
- 集成测试（打真实归档）放到 M3，并只对 fixture 目录做
